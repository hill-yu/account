# 权威日报刷新与北京时间小时查询设计

- 日期：2026-08-05
- 状态：需求已确认，待实施
- 开发基线：生产快照 `355a24e`
- 开发分支：`dev`
- 对接系统：`adx-user-system`

## 1. 目标

1. 权威日报按账户时区业务日 D+1 的 05:00、06:00、07:00 各拉取一次。
2. 每次成功拉取都作为正式版本；后一次成功结果无论增加还是回滚下降，都覆盖当前版本。
3. 任一次拉取失败或数据不完整时保留原版本，不允许部分覆盖。
4. 小时任务只维护小时数据，不再覆盖权威日报。
5. user_system 按 `report_date` 查询小时数据时，该日期固定解释为北京时间自然日。
6. 不回补历史数据；07:00 后如仍有异常，由人工刷新处理。

明确不修改 `adx-user-system` 代码，不增加指标异常告警；本项目只提供保持兼容的中台接口和对接说明。

## 2. 权威日报规则

### 2.1 调度

每个启用权威日报的账户，根据账户自身时区计算业务日结束后的时间：

- 05:00：第一次拉取；
- 06:00：第二次拉取；
- 07:00：第三次拉取。

三个结果都不区分 provisional/finalized，均可通过现有日报 API 返回。user_system 自行在账户时区 07:00 后同步，不要求中台日报 API 新增完成标志。

### 2.2 覆盖规则

- 只要本次 Google 日报完整拉取并成功入库，就整体替换该账户、该业务日的当前日报。
- 后一次数据允许高于或低于前一次；不使用“只保留更高值”规则。
- 网络、解析、日期校验或 Google 分页任一环节失败时，本次任务失败并保留旧值。
- 所有 Google 分页成功，是指本次报表包含的每一页都成功下载、解析和校验后，才允许替换当前日报；例如第 1 页成功、第 2 页失败时不得写入半份数据。
- 合法的完整零数据可以覆盖；请求失败或空响应不能当作合法零数据。

最小实现边界：collector 先在本次任务内完成核心日报、日报维度及其全部 Google 分页的下载和校验，在全部成功前不向当前日报表提交数据；全部成功后，通过一次权威日报替换请求提交完整结果。中台在单个数据库事务内同时替换该账户业务日的核心日报和日报维度投影并标记任务成功。任一部分失败则整个事务回滚，不引入逐页直接投影，也不新增通用 staging/finalize 流程。

05:00、06:00、07:00 使用固定槽位顺序。相同账户和业务日同一时刻只允许一个自动日报任务写入；更晚槽位任务成功发布后，较早槽位即使迟到完成也必须被拒绝，不能反向覆盖。该保护只需记录并比较当前已发布槽位序号，不扩展为通用 generation 系统。

### 2.3 数据保存

- 日报主表仅保存当前正式版本，避免重复保存完整明细。
- 每次成功只额外记录轻量版本摘要：账户、业务日、任务、拉取时间、指标汇总、行数和哈希。
- 不保存每个历史版本的完整 payload；不在对接 API 增加必须字段。
- 小时入库逻辑不得删除、重建或更新权威日报表。

### 2.4 人工刷新

07:00 后如发现 Google 再次调整数据，由 operator 鉴权接口手动触发指定账户、指定业务日的权威日报刷新。成功时按相同规则整体覆盖，失败时保留当前版本。重复请求须幂等，同一账户和业务日不得并发覆盖。

## 3. 北京时间小时查询

user_system 继续使用现有 `report_date=YYYY-MM-DD` 参数，不改 URL 和指标字段。该日期统一表示北京时间 00:00–23:59。

例如请求 `report_date=2026-08-05`，数据库按以下 UTC 左闭右开区间查询：

```text
report_time_utc >= 2026-08-04 16:00:00Z
AND report_time_utc < 2026-08-05 16:00:00Z
```

查询以 `report_time_utc` 为准，不再用采集任务或数据行的源 `report_date` 过滤。账户时区、源日期和 `source_timezone` 保持原值，仅对外查询窗口和返回日期按北京时间换算。

以下小时接口必须使用同一换算函数，确保明细、总数、分页和覆盖小时口径一致：

- `/api/v1/operator/reports/account-hourly`
- `/api/v1/operator/reports/site-hourly`
- `/api/v1/operator/mid-platform/reports/account-hourly`
- `/api/v1/operator/mid-platform/reports/site-hourly`
- `/api/v1/operator/mid-platform/reports/account-hourly-dimensions`
- `/api/v1/operator/mid-platform/reports/site-hourly-dimensions`

## 4. 失败与兼容处理

| 场景 | 处理 |
|---|---|
| 05:00 或 06:00 失败 | 保留最近成功版本，下一时间点继续执行 |
| 07:00 失败 | 保留最近成功版本，后续按需人工刷新 |
| 任一分页失败 | 整次失败，不覆盖旧版 |
| 新版指标下降 | 正常覆盖，视为 Google 合法回滚 |
| 重复任务 | 幂等处理，不产生重复当前版本 |
| 小时任务成功 | 只更新小时事实，不改日报 |

兼容边界：不修改 OAuth、代理、collector 节点拓扑、小时任务频率、日报指标公式和 user_system 现有日报字段。小时接口日期语义由源日期调整为北京时间自然日，发布前必须执行接口契约回归。

非目标：不修改 `adx-user-system` 代码、不做指标异常告警、不回补历史数据，也不增加 finalized/provisional 对接字段。

## 5. TDD 实施顺序

1. 先写失败测试，证明小时任务当前会改写日报，并固定“小时不写日报”的新边界。
2. 写 05:00、06:00、07:00 三次调度及幂等测试，再做最小调度修改。
3. 写完整结果整体覆盖、下降覆盖、分页失败不覆盖、零数据边界测试，再实现日报替换事务。
4. 写 05:00/06:00 迟到任务不能覆盖 07:00 成功版本的测试，再实现最小槽位顺序保护。
5. 写旧完整 payload 不保留、轻量摘要保留的测试，再实现精确清理。
6. 写人工刷新鉴权、幂等和失败保留测试，再增加最小 operator 接口。
7. 写北京时间跨 UTC 日期查询测试，再统一六个小时接口的时间窗口。
8. 运行后端和 collector 全量测试，完成独立审阅后才允许真实账号测试、Git 提交和部署。

## 6. 验收标准

- 同一账户业务日可在 05:00、06:00、07:00 各成功刷新一次。
- 后一次完整结果无论增减均成为当前日报。
- 任一分页或写入失败均不会改变旧日报。
- 小时任务不再改变权威日报。
- user_system 查询北京时间日期时，可覆盖该自然日对应的两个 UTC 日期区间，无遗漏、无重复。
- 不新增 user_system 必须消费的 finalized/version 字段。
- 不修改 `adx-user-system` 代码，不新增指标异常告警。
- 历史完整日报 payload 不重复保留，只保存当前版本和轻量摘要。
- 不改变 OAuth、代理、调度频率或其他未授权生产行为。

## 2026-08-05 接口契约更正

隔离联调确认，现有 `user_system` 会严格检查日报记录的 `is_finalized is true`，缺少该字段的记录不会入库。因此，上述“不新增完成标志”的边界不再适用：中台五个日报读取接口须在每条中台已入库、当前正式可消费的权威日报记录上返回 `is_finalized: true`。该字段表示中台允许消费方正式入库，不表示 Google 后续不会延迟更新或回滚；也不追溯证明旧版写入路径的全部分页原子性。该修正是兼容现有消费方的附加字段，不修改 `user_system`、数据库、调度和小时接口，也不引入处理中间态或版本字段。
