# 维护手册按问题类型分类索引设计

## 1. 目标

在不移动、不改写 `docs/system-maintainer-onboarding-guide.md` 第 22 节原始追加式台账的前提下，新增按问题类型分类的导航索引，使维护人员能够按问题领域快速定位历史变更，同时保留完整时间顺序和审计证据。

成功标准：保持原始时间顺序，新增“按问题类型分类索引”。

## 2. 设计原则

1. 第 22 节所有历史记录继续按日期顺序排列，正文不移动、不拆分、不复制。
2. 分类索引位于“记录模板”之后、首条正式历史记录之前。
3. 一条记录可归入多个问题类型，不强制单选。
4. 索引只保存日期、标题、状态摘要和文档内链接，不复制实施正文。
5. 分类依据是记录解决的问题和主要影响面，不以修改的文件类型机械分类。
6. 后续新增第 22 节记录时，必须同步更新分类索引。
7. 索引链接使用稳定的显式 HTML 锚点，避免中文标题自动锚点在不同 Markdown 渲染器中不一致。
8. 不在索引中写入密码、Token、OAuth code/state、client secret、refresh/access token、完整代理凭据或生产数据。

## 3. 分类结构

### 3.1 开发治理、Git 与工作树

覆盖开发流程、TDD、独立审阅、分支、worktree、提交、发布基线和交接治理。

### 3.2 生产部署、环境与 systemd

覆盖服务器运行路径、环境文件、systemd、部署一致性、服务启停和回滚。

### 3.3 OAuth、凭据与管理员认证

覆盖 OAuth 授权、凭据版本、健康检查、Token 状态、管理员登录和认证接口。

### 3.4 代理与采集运行时

覆盖代理绑定、出口验证、collector runtime、采集环境和真实链路验证。

### 3.5 调度、灰度与任务治理

覆盖 scheduler、fetch schedule、灰度名单、停拉规则、任务幂等、退避和任务范围。

### 3.6 小时报表与跨日完整性

覆盖 Pacific 源时区、小时任务、跨日最终刷新、小时缺口、覆盖范围和小时数据完整性。

### 3.7 权威日报与数据保护

覆盖权威日报成熟窗口、finalized 状态、日报刷新、小时任务禁止覆盖日报及定向恢复。

### 3.8 维度报表与 API 兼容

覆盖国家、广告单元等维度、指标扩展、日期范围、API 响应兼容和 user_system 对接。

### 3.9 前端与管理界面

覆盖管理员登录、账号/OAuth 页面、任务分页、加载策略和界面兼容。

### 3.10 节点接入与运维复盘

覆盖新节点接入、重授权、节点恢复、接入错误、操作复盘和防再犯。

### 3.11 架构研究与新方案

覆盖 Service Account PoC、新平台架构、迁移设计和未直接进入生产的研究方案。

## 4. 索引条目格式

每个分类使用表格：

```markdown
| 日期 | 记录 | 状态 |
| --- | --- | --- |
| 2026-08-05 | [权威日报自动尝试窗口调整为业务日结束后五小时](#change-2026-08-05-daily-maturity-window) | 已发布 |
```

状态仅从原记录明确结论中提炼，使用以下有限词汇：

- 已完成
- 已发布
- 已灰度
- 已回滚
- 部分完成
- 待处理
- 仅设计/研究
- 文档治理

原记录没有足够证据时使用“状态见原记录”，不得推测。

## 5. 稳定锚点规则

在每条第 22 节正式记录标题之前增加显式锚点：

```html
<a id="change-2026-08-05-daily-maturity-window"></a>
```

锚点命名规则：

```text
change-YYYY-MM-DD-简短英文主题
```

要求：

- 全文唯一；
- 仅使用小写 ASCII 字母、数字和连字符；
- 不改变原有 Markdown 标题文字；
- 同日多条记录使用不同英文主题，不使用序号占位。

## 7. 文件变更范围

- 修改 `docs/system-maintainer-onboarding-guide.md`：增加分类索引、稳定锚点、本次第 22 节记录。
- 修改 `docs/问题记录.md`：记录当前维护手册难以按问题类型检索的问题、解决方案与验证结果。
- 创建本设计文件及对应实施计划。

不修改代码、数据库、服务、配置、OAuth、代理、任务、灰度、schedule 或生产环境。

## 8. 验证标准

1. 第 22 节原有记录标题及其相对顺序完全不变。
2. 每条正式记录都有唯一显式锚点。
3. 分类索引中的每个链接均能找到对应锚点。
4. 每条正式记录至少出现在一个分类中。
5. 每个索引条目都对应真实历史记录，不新增推测性状态。
6. `git diff --check` 通过。
7. 敏感信息字面量扫描通过。
8. 独立审阅无 P0/P1 后才允许最终提交与推送。

## 9. 回滚方式

仅删除新增分类索引、显式锚点、本次第 22 节记录和对应问题记录；不得回滚、移动或覆盖任何既有历史台账正文。

## 10. 后续维护规则

每次追加第 22 节记录时同时执行：

1. 为新记录添加唯一显式锚点。
2. 将记录加入至少一个问题类型。
3. 从原记录提取状态；证据不足时写“状态见原记录”。
4. 验证索引链接和锚点唯一性。
5. 在提交前运行文档差异和敏感信息检查。
