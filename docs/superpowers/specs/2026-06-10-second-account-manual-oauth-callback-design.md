# 第二账号手动 OAuth 回调地址设计

**日期：** 2026-06-10  
**状态：** Draft for review

## 1. 背景

当前控制台已经支持以下能力：

- 新建账号
- 为账号创建一个执行节点（`collector_instance`）
- 为账号创建一套 OAuth 配置（`oauth_app_config`）
- 在 OAuth 配置里手动填写 `redirect_uri`

这套模型本身已经满足“一账号一节点”的运营方式，也支持新增第二个账号，再为第二个账号单独配置节点和 OAuth。

当前缺口不在后端能力，而在操作可见性：

- 界面没有明确强调“每个账号都要填写自己网站对应的回调地址”
- OAuth 列表没有直接展示 `redirect_uri`
- README 和操作说明没有把“第二账号接入”的手动步骤说清楚

这会导致在新增第二个账号时，操作人员容易沿用第一个账号的网站回调地址，造成授权回流到错误站点。

## 2. 目标

本次设计的目标是：

**在不改变现有一账号一节点、一账号一套 OAuth 配置模型的前提下，让第二个账号可以清晰、稳定地配置自己独立的网站回调地址，并降低人工填写错误概率。**

## 3. 范围

### 3.1 本次要做

- 保持现有后端数据模型不变
- 保持 `redirect_uri` 继续手动填写
- 优化前端文案，让操作人员明确知道该字段应填写“当前账号对应网站”的回调地址
- 在前端列表中展示 `redirect_uri`，方便核对
- 在文档中补充“新增第二个账号”的手动操作说明

### 3.2 本次不做

- 不新增“网站域名”“回调基地址”之类的新字段
- 不自动根据节点信息推导 OAuth 回调地址
- 不支持一个账号绑定多个节点
- 不支持一个账号绑定多套 OAuth 配置
- 不调整现有授权回调后端接口路径

## 4. 现状约束

当前实现里有两个关键约束：

- `collector_instances.account_id` 是唯一值，所以一个账号只能对应一个节点
- `oauth_app_configs.account_id` 是唯一值，所以一个账号只能对应一套 OAuth 配置

这两个约束与本次目标一致，因此本次不做数据库迁移。

## 5. 推荐方案

推荐采用“最小代码方案”：

1. 保留现有后端接口和表结构。
2. 保留 OAuth `redirect_uri` 手动输入。
3. 通过前端提示、列表展示和 README 流程说明，显式支持第二个账号接入。

选择这个方案的原因：

- 完全符合“暂时可以接受手动输入后端添加节点”
- 不引入额外字段和迁移风险
- 不会影响现有单账号流程
- 可以立刻支持第二个账号独立配置回调地址

## 6. 交互设计

### 6.1 Instances 区域

`Instances` 区域保持现有字段结构不变。

这里仍然用于登记第二个账号对应的节点信息，例如：

- 实例名称
- 预期出口 IP
- 节点 `report_base_url`
- 节点 `report_account_key`
- 节点 `report_token`

界面文案需要强调：

- 第二个节点不是挂在第一个账号下
- 而是先创建第二个账号，再为第二个账号创建它自己的实例

### 6.2 OAuth Apps 创建表单

`Redirect URI` 字段继续手动填写，但提示文案要改为更明确的说明，例如：

- 请填写当前账号对应网站的 OAuth 回调地址
- 不同账号可以使用不同网站地址
- 不要复用其他账号的网站回调地址

默认值仍可保留当前前端回调地址，用于本地开发；但文案要明确这是默认开发值，不代表生产或正式站点配置。

### 6.3 OAuth Apps 列表

列表中新增 `redirect_uri` 展示列，至少满足以下目标：

- 操作人员能一眼看出每个账号配置到了哪个网站
- 新增第二个账号后，可以快速核对是否误填成第一个账号的回调地址

如果列表宽度受限，可以允许该列换行显示，但不应隐藏该信息。

## 7. 文档设计

README 需要补充“新增第二个账号”的最小操作流程：

1. 创建第二个账号
2. 创建第二个账号对应的实例
3. 创建第二个账号自己的 OAuth 配置
4. 在 `redirect_uri` 中手动填写第二个账号对应网站的回调地址
5. 生成授权链接并完成授权

文档还需要明确：

- 一个账号对应一个节点
- 一个账号对应一套 OAuth 配置
- 不同账号的回调地址可以不同
- 当前版本不自动从节点信息推导回调地址

## 8. 后端影响

本次后端不需要改动接口契约。

原因如下：

- `OAuthAppCreate.redirect_uri` 已经支持手动填写
- `OAuthAppRead.redirect_uri` 已经存在
- `CollectorInstance` 已经支持按账号创建节点

因此本次主要是前端展示和文档补充，不涉及数据库迁移和 API 契约变更。

## 9. 风险与防错

本次最大的风险不是程序错误，而是人工误配置。

主要风险：

- 给第二个账号误填第一个账号的网站回调地址
- 误以为“第二个节点”要直接挂在第一个账号下

对应防错措施：

- 在 OAuth 表单中强化字段提示
- 在 OAuth 列表中显示 `redirect_uri`
- 在 README 中明确“第二个账号”的操作顺序

## 10. 验收标准

本次完成后，应满足以下结果：

1. 操作人员可以继续通过现有流程创建第二个账号和它自己的实例。
2. 操作人员在创建第二个账号的 OAuth 配置时，界面会明确提示应填写该账号对应网站的回调地址。
3. OAuth 列表能够直接看到每个账号当前配置的 `redirect_uri`。
4. README 能指导新增第二个账号的手动接入流程。
5. 现有单账号本地开发流程不被破坏。

## 11. 实施边界

如果后续你希望做到以下能力，应作为下一轮需求单独设计：

- 从实例或站点域名自动生成 OAuth 回调地址
- 一个账号下支持多个节点
- 一个账号下支持多套 OAuth 配置
- 为不同环境（本地、测试、正式）维护不同默认回调地址
