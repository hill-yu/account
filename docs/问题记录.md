# 问题记录

## 2026-08-11：测试服务器小时任务按错误调度时区计算报告日期

### 现象与原因

测试服务器 `cpatobe` 的小时计划使用 `Asia/Shanghai`，但 Google 小时数据源固定按 `America/Los_Angeles` 业务日生成。北京时间先跨日后，scheduler 把北京时间日期直接作为 `report_date`，从而请求 Pacific 尚未到达的未来业务日；任务状态可成功，但批次为 0 行。旧逻辑在 Pacific 跨日后也不会回查上一业务日，可能永久缺少延迟到达的源小时 23。

### 修复方案

1. 测试环境将 `cpatobe` 的计划时区改为 `America/Los_Angeles`，保留 48 个半小时触发点，执行频率不变。
2. 复用生产已验证的跨日收尾机制，新增默认关闭的 `ADX_COLLECTOR_CROSS_DAY_FINALIZE_ACCOUNT_KEYS`，测试环境仅配置 `cpatobe`。
3. Pacific 01:00–02:59 的正常调度周期在上一业务日尚无成功收尾时刷新上一业务日；不增加额外任务频率。
4. 收尾任务使用 `run_reason=cross_day_finalize` 和确定性请求 ID；成功不重复，失败最多两次，耗尽后记录唯一 blocked 标记。
5. 功能仅在 `direct_collector_only=true` 时启用，不改变日报、OAuth、代理、生产调度或历史数据。

### 配置与安全

测试实例使用 `report_account_key=cpatobe` 和本机端点 `http://127.0.0.1:9123`。`report_token` 由服务器生成并仅存于受限环境文件和数据库，不写入 Git、文档或日志。真实链路测试仅使用已授权的 `cpatobe` 及其既有测试代理。

### 验证与回滚

定向 scheduler 回归覆盖首次收尾、幂等、普通活动任务隔离、收尾活动任务复用、两次失败上限、窗口外、开关外、非 direct 模式和 DST 回拨边界。首次独立审阅发现收尾任务可能错误复用普通 `preview` 活动任务的 P1；第二轮复审进一步发现真实入口仍存在相同的提前返回。两处均已按 TDD 修复：finalize 的入口查询和创建查询都只复用 `run_reason=cross_day_finalize` 的活动任务，并由真实 `trigger_manual_fetch` 入口级测试验证。修复后后端全量 166 passed；最终独立复审 P0/P1/P2 均为 0。代码提交 `f092cc5` 已发布到测试服务器；真实任务 296 对上一 Pacific 业务日执行成功，小时维度批次 6 行，账户/站点小时数据均有 Requests。回滚时清空白名单、恢复计划时区及备份目录 `20260811T083528Z-pre-crossday-finalize` 中的环境文件/数据库，并将 Git 回退到 `315bf67`，不触碰生产服务器。
