## 2026-08-06：源时区跨日后未回查上一业务日，造成北京时间小时数据缺口

### 现象与根因

小时源固定为 `America/Los_Angeles`。scheduler 在源时区跨日后立即把 `report_date` 切换到新日期，不再回查上一源业务日。如果上一业务日最后一小时尚未被 Google 返回，该小时会永久缺失。PDT 下源小时 23 对应次日北京时间 14:00。

生产只读审计确认该问题具有共性：2026-08-09 的北京时间 14:00 同时在 `coeurdazur`、`cpatobe`、`linkzclub`、`onlyfungogo`、`reboroots`、`skouje` 缺失；2026-08-10 同一小时在其中五个仍缺失。对应源日期均为 `00–22`，缺少源小时 23。日期结束后人工拉取的 `tqchq.com` 可得到完整 `00–23`，验证了根因。

低量账号不足 24 个非空小时不等于存在缺口，因为 Google 可能不返回真实零数据小时；不得据此批量重拉。

### 统一代码整改

1. 通过 `ADX_COLLECTOR_CROSS_DAY_FINALIZE_ACCOUNT_KEYS` 明确控制灰度账号，默认关闭。
2. 在 Pacific 新业务日 01:00–02:59 的正常小时调度周期，若上一源日期尚无成功最终刷新，则用本周期重拉上一源日期，不额外增加任务量；下一周期恢复当前日期。
3. 任务标记 `run_reason=cross_day_finalize`，使用确定性请求 ID；成功后不重复，活跃任务复用，失败最多重试一次；两次失败后写入唯一的 `cross_day_finalize_exhausted` 阻塞记录，避免缺口静默。
4. 最终刷新只替换该账号、该 Pacific 源日期的小时分区，不写入或重建账户/站点权威日报。
5. 历史缺口不自动回补，仍须逐账号、逐日期备份和受控处理。
6. 本功能只在 `direct_collector_only=true` 时生效；非 direct 模式继续执行原当前日任务，避免旧远端协议在调用前无法落库而突破幂等和重试上限。

### 验证与发布边界

TDD 覆盖首次回查、成功幂等、活跃任务复用、两次失败上限、窗口外和开关外不回查、DST、任务标记落库，以及小时批次不覆盖权威日报。代码必须通过独立审阅和 Git 提交后，先仅对 `coeurdazur` 灰度并观察两个 Pacific 跨日周期；未验证前不得扩大节点范围。

2026-08-11 后续经用户明确授权扩大灰度。扩大范围仅包含 OAuth 健康且已授权、代理有效、每小时 schedule 已启用且使用 Pacific 调度时区的节点：`coeurdazur,cpatobe,dddfdc,ddgjcj,linkzclub,onlyfungogo,reboroots,skouje,tqchq,uragnv,zilote`。`stones` 的计划间隔为 4 小时，可能错过两小时最终刷新窗口，因此未纳入；其他停用或授权不满足门禁的节点也未纳入。

### 回滚

清空灰度账号配置即可立即停用新行为；代码回滚不涉及数据库迁移。必要时定向取消该账号尚未执行的 `cross_day_finalize` 任务，不做整库恢复。

## 2026-08-12：linkzclub OAuth 实际失效但状态仍健康，导致任务风暴与数据中断

### 事故现象与根因

`linkzclub.com` 的小时事实水位停在北京时间 2026-08-09 23:00，权威日报停在账户业务日 2026-08-08。账号、实例、schedule、代理及数据库 OAuth 状态表面均正常，但从北京时间 2026-08-10 02:06 左右开始，小时与日报任务同时持续失败。隔离检查确认代理实际出口仍与期望出口一致；使用活动 v2 托管凭据分别经代理和直连 Google token endpoint，均返回 `Token has been expired or revoked.`。根因是 refresh token 已撤销或过期，而数据库仍错误保留 `authorized + healthy`。

### 暴露的问题

1. collector 把底层异常统一回传为 `collector_task_failed`，OAuth、代理、SOAP、超时等原因无法从任务日志区分。
2. OAuth `runtime_status` 未因真实 token 刷新失败及时转为 revoked/degraded，schedule 继续创建必败任务。
3. 权威日报失败后约每 30 秒重复创建新任务，单日累计超过千条，缺少按账号/报告日幂等和退避。
4. 代理表的 `active` 与健康检查时间可能长期陈旧，排障不能只信数据库状态。
5. 健康检查任务实际 `succeeded`、OAuth 已恢复 `healthy`，但日志 message 却为 `oauth_validation_failed`，终态和日志语义矛盾。

### 本次恢复结果

仅对 account 33 / OAuth App 32 执行强制重授权。callback 兑换生成 staged v3；凭据验证任务成功后 v3 激活、v2 退休；OAuth 健康检查成功，最终恢复 `authorized + healthy`。代理、schedule 和其他账号未修改。兑换前在线 SQLite 备份为 `/srv/adx-account-isolated-collector/backups/20260812T065900Z-pre-linkzclub-callback-exchange`，`quick_check=ok`。

### 后续代码整改

需要另立 TDD 任务：保留安全脱敏后的失败分类；token endpoint 明确返回 revoked/expired 时立即打开 OAuth 熔断；权威日报失败按账号+报告日幂等并指数退避；健康检查成功日志不得写失败文案；健康汇总应暴露代理检查陈旧度。整改前不得以数据库 `healthy` 单独证明 OAuth 可用。
- 2026-08-12 数据恢复：OAuth v3 恢复后，仅对 `linkzclub.com`（account 33）串行补拉。小时任务 `25346—25349` 全部成功；8 月 8—10 日各 24 小时，8 月 11 日为 Google 当前返回的 12 个非空小时快照。权威日报任务 `25350/25352/25354` 分别恢复 8 月 9—11 日并成功。补拉前备份 `20260812T072216Z-pre-linkzclub-backfill` 校验正常，小时补拉未覆盖既有权威日报。
- 2026-08-12 操作问题：首次日报补拉在客户端等待超时后仍于服务器后台继续，直接重跑脚本触发相同 `external_request_id` 唯一约束；数据库安全拒绝重复插入，未造成重复业务任务。以后必须先查既有请求号/任务终态再决定是否重试，禁止把客户端超时当成服务器未执行。
## 2026-08-13：治理规则仅存在任务分支，尚未成为 master 正式基线

### 背景、现象与影响

根目录 `AGENTS.md` 在其所在 worktree 内实际生效，但新增启动门禁和文档统一规则此前只提交在 `codex/production-ops-handoff`。远程 `master` 仍为 `b157a63`，该任务分支领先 9 个提交；直接合并会夹带分类索引和交接文档等其他成果。未单独集成前，新建于旧 `master` 的 worktree 无法获得最新规则。

### 根因、解决方案与验证

根因是 Git 分支隔离，而非 `AGENTS.md` 文件位置错误。解决方案是从最新 `origin/master` 创建临时集成 worktree，只移植根规则 9、14–16、维护原则同步文字和本条最小追加记录，不 cherry-pick 原分支提交、不复制整份维护文档。完成差异检查、独立审阅和提交后，仅以 fast-forward 更新 `master`。

首次范围校验直接比较 `git diff --name-only` 与中文路径，因 Git 默认转义中文路径而误报缺少 `docs/问题记录.md`；门禁立即停止，未提交、未推送、未影响 `master`。正确命令必须使用 `git -c core.quotepath=false diff --name-only` 后再比较精确文件集合。

独立审阅确认 P0/P1 均为 0，可以提交；P2 要求更新前再次 fetch 并只允许 fast-forward，远程 `master` 若移动必须停止并重新移植、验证和审阅。实施提交为 `cd2bcc7`，台账闭环提交紧随其后生成。当前状态：本地最小补丁已通过审阅，等待 master 快进。影响仅为 Git 文档；未连接生产。遗留风险是既有 worktree 即使 `master` 更新也不会自动同步，继续任务前仍须显式同步。若集成失败，保留 `master` 不变并删除临时分支/worktree；不得重写远程历史。
